以上是**目标跳转关系**，不是声称全路由已实现。已有业务程序保持各自页面、各自内部导航和状态。菜单的顾客匿名使用不应出现“返回员工工作台”；只在来自受保护POS的可信同会话情形，允许显示“返回门店点单台”，不得仅因前端query\`from=pos\`就授予内部权限。

统一导航组件\`ReturnToWorkbench\`是一条**小而持续可见**的链接；\`BackToOrigin\`用于本程序内部安全返回上一步，若历史记录来自外部、已注销、受限页或无法确定来源，则直接返回本程序主页或工作台（按身份权限），不能盲目\`history.back()\`进入旧员工私有页。跨程序返回时对未提交表单提醒“保存草稿/放弃”，避免错误丢单或丢审批；不复制完整程序内容至工作台。工作台仍负责展示链接，不作为其他程序状态的二级数据源。

## 2. POS唯一视觉方案：以原地图为中心做局部改造

### 保留的版式骨架
1. **原门店登录/门店核验页面保留**，选地区/店、设备、当班资格等原检查照常执行；不把所有人带入通用工作卡。
2. **原侧导航**保留“座位点单、进行中桌次、待出品队列、清洁任务、历史结账、操作记录”功能及其\`data-page\`切换。可以对最需要的提醒加强标志，但不能删除入口。
3. **原顶部**保留当前店名、本人、当前系统状态、刷新、电子菜单、总部授权入口和换店；只增一个小的“← 返回工作台”，不在顶栏重造一整套全公司功能目录。
4. **原地图**\`#floorStage + .floor-svg + #seatLayer + #seatNavigator\`保持可见性和交互；在PC/平板优先展示。无地图的店如实显示“本店图纸待导入”，**绝不借用其他店图**。
5. **原右侧/详情点单区**\`#orderPanel\`和原弹窗继续使用现有下单、人员数、商品搜索、支付登记、转桌、撤单逻辑。高频的“确认下单/进入制作”可优化视觉优先级，但不得移除确认步骤或让普通点击直接触发有价订单。
6. **原下方/独立页的出品和清洁队列**与原审计历史继续保留；未完成任务允许在红色警报上显示快捷定位，点击回到对应现有\`setPage('queue'|'clean')\`，不新造第二个任务数据库。

### 局部警报层（复用原有实现）
- 源码已有\`severity(),renderAlerts(),critical-overlay\`及超时阈值，不能重复造另一套可写警报/计时器。
- 绿/黄/红/灰**同时配中文和图形**。P0真实食品安全风险需要由业务owner阻断受影响批次；P1严重服务等待或卫生清洁可首发一次红色全屏提醒，确认后继续保留红色顶栏/原\`#alertStrip\`直至真实事件解决；P2琥珀预警、P3普通任务仅显示相关局部卡。**红屏不能永久占据整个POS使员工无法处理座位和订单**。
- 严重超时屏必须明确“哪个座位/卫生间、发生什么、已经多久、立即进入哪一原工作区”。点击“我已看到”只记录ack，不得伪造卫生已处理或商品已送达。P0不能靠关闭弹层解除批次安全冻结。
- 危险操作按钮颜色采用红色，但同屏必须说明影响对象和后果。状态实际来源必须为原有服务或后来正式 owner API，不能前端硬编色彩使业务状态改变。
- **地图区域的布局变化不得改变座位坐标计算、SVG视口、触控命中区域、旧座位确认弹窗或转桌顺序。**

### 进入POS后的信息层级（原功能不减少）
- 第一层：**地图本身 + 当前门店 + 当前操作者**；
- 第二层：地图上叠加的状态座位、待出品数/清洁逾期数及极少量最紧急提醒；
- 第三层：正在选择的座位/订单操作栏；
- 第四层：历史、审计、配置/资料库等通过原独立业务页/导航打开。

不能因为“工作台首页只显示一个主任务”就把POS首页也做成一个主任务大卡。**员工工作台与门店地图是两种不同场景，不能套同一套页型。**

- 颜色不是唯一提示；必须同时有中文状态词与图形。安全红只用于P0/P1及危险动作，不把普通业务页面刷成红色。
- 手机宽度320/375/390/768及Windows 1024/1440下分别验收。原POS地图需保持稳定视口、可滑/缩、桌位可点击，输入法不能遮挡主操作/警报按钮。
- 保留已有\`prefers-reduced-motion\`逻辑、焦点可见、键盘和屏幕阅读器通知；动画只加状态变化的短暂反馈，不以华丽转场替代可用操作。
- 员工和顾客可见文案使用最终对人表达；隔离未上线、未真实收款的页面仍必须明确标明测试/禁用事实，不能为了美观伪装真支付成功。
