## Architecture and execution
One existing platform, 8 independent development worktrees, no 8 new services. Existing POS owner owns order/visit write path, C public projections only, A single resolver and configuration registry (not second policy owner), B identity, D noncash assets, E commission liability, G third-party fact, H payments/refunds/payouts. Shared files and migrations one integrator. Prefer direct calls inside existing service; across actual service boundaries use approved APIs and durable events; only existing transactional store or equivalent, no additional broker unless measured need.
R0 A baseline and synthetic tenant/refs; C existing public read can proceed independently. R1 B/C customer entry; R2 D/E base rights and attribution; R3 F POS order bridge; R4 G official manual or authorized external; R5 H actual payment/refund + F/D/E verified events; R6 optional paid programs, booking, stock, store commercial expansion. Order is dependency guidance, not imposed chronology. Parallel fixture development not dependent on actual credentials. Production gates by module. Keep POS hot-upgrade patches in common integration baseline.
