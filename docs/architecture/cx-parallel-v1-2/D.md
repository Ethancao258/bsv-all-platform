## 实现顺序
D1 将既有首访/返场条件、有效期、折扣、指定赠饮SKU、门店、次数、叠加规则引用 policy.membership/benefit，发布时冻结版本。D2 规则判断：tenant/customer匹配、有效期左闭右开、消费事实、适用门店/产品/次数、互斥/叠加，服务端输出可用原因。发放唯一键(来源事件,客户,权益类型,政策版本)。D3 锁定权益/余额；预占→提交→消费或释放；超时先核对支付/履约终态，未知不释放导致双用；补偿以冲正事件记录，不覆盖。可用数量=发放+合法调整-已消费-活动预占；存量不得为负。已有表字段兼容性由数据owner确认。D4 总部赠礼/批量发放、沉睡客户筛选以最近真实消费及同意状态；发送与发放分离、dry-run去重；纸卡扫码定位电子权益而非直接授予。D5 存酒仅员工确认，实物编号、商品/门店/容量/单位/证据/有效期/办理人/流水；取酒申请进入F服务任务，实际员工扣减；到期按事先告知规则处理，不能自动删账。D6 计时共用服务session，UTC起止/暂停（按政策）、费率/档位冻结，服务器计算剩余或应收，客户端仅展示；积分/次卡按单独单位流水。商品/计时服务报价仍由F/H。
