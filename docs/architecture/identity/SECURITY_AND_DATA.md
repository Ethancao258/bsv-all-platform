# 身份、权限与数据安全模型｜R2

## 授权不依赖易猜编号

`TRA0001` 只回答“是谁”，`EMPA0001` 仅表明员工阶段历史，`BMA0001` 表示管理阶段历史；**身份代码永远不是凭据**。权限判定条件依次为：服务/浏览器已经认证 → 服务端 token/cookie 可撤销且未到期 → auth_subject_id 活跃映射到唯一 TR → TR 未暂停/删除 → 当前法人有效任职 → 阶段已颁发（EMP/BM）→ BM 当前任命（仅管理动作）→ 角色/具体动作/门店授权有效 → 对应资格有效（POS 必需 `POS_SERVICE`，供货必需 `SUPPLY_SAFETY`）。全部从 A 事务查询；`cache_ttl_seconds=0`，A 故障拒绝。

## 权限最小化和职责分离

- 申请人自己不能批准自己的 TR、任职、EMP/BM、授权或恢复申请；核验和审批须两个独立管理员账号。**演练使用两个虚构账号**，不代表已经实现真实人的防串谋、法定代表人审批或实名多因素认证。
- 作用域：法人 `legal_entity_id`、门店 `store_id`、`action`、时间有效期；不能凭“总部”字符串跨法人读取记录。
- 高风险 `pos.order.create`、`supply.batch.receive` 等依赖独立有效资格；不得提交任意空 qualification 绕过必要检查。
- 审计 append-only（PostgreSQL 候选触发器），本人、总部审计读取各自范围；不存身份证/密码/真实支付资料。隐私删除必须双人确认、留最小不可再分配 TR 占用墓碑。
- 撤权后服务端实时查 A；个人会话在适用场景撤销。浏览器防 CSRF，跨域来源判定，HttpOnly + SameSite cookie，CSP/XFO/no-store；正式还需 HTTPS、可信反代、网络 ACL、WAF、分布式限流。

## 认证适配的真实状态

- `isolated`：Argon2 密码哈希账号，**只可在隔离环境**做流程演练；其表 `bsv_identity_isolated_users` 在独立 `IsolatedBase`，不参与正式业务 DDL 候选，生产启动直接拒绝测试认证。
- `cloudbase_jwks`：源码已定义带 issuer/audience/expiry 的 RS256/ES256 JWT 验签候选；**实际 CloudBase Auth 令牌格式、验签密钥和部署流程未核实，不能宣称已打通**。正式改用已核验的原集团认证契约，保留一致的业务 `auth_subject_id` 映射，严禁出现第二个认证主库。
- 服务端调用 `/api/v1/identity/authorize` 使用长随机服务凭据、事先限制的法人/门店/动作范围；正式应替换为已有机器身份或 mTLS 凭据并做轮换，不能放进网页 JavaScript。

## 个人资料、保留与纠错

代码只要求最小化展示名和可选摘要核验线索，申请者须明确同意当前公示的用途和保留期；**当前页面文字并非法务核准的正式个人信息处理规则**。现实员工账号恢复、应聘资料保留、劳动关系证据、申诉更正、基于法定义务的工资/工时记录保存都需要单独规章和审批，不因 TR 退出而自动删除客观劳动事实。生产审计与加密备份可能含敏感资料，须制定保留上限、删除队列和访问审批。

## 已知残余风险/生产阻断

1. 真实自然人去重没有可靠外部身份证明或实名认证；仅用摘要线索＋人工两人审核，不能独立证明“每人终身唯一”在真实世界 100% 落地。
2. 多实例/多节点限流需要生产网关或分布式服务；本包的防猜解限流不保证跨 worker / IP 欺骗防护。
3. PostgreSQL 17 运行时并发锁、触发器执行、数据库权限和恢复未在本环境实测（只生成/模拟编译 DDL）。
4. 实际组织门店注册表、学习资格签发方、POS/供货接口调用者及合同规则尚未接入生产验证。
5. 生产 PostgreSQL RLS/GRANT、行级审计、可靠异地备份及合法保留政策需 G0/G1 现场核查，不能在本包对现有云表盲写。
